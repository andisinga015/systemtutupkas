# Penyebab GET besar dan patch writer V4.2.1

## Jalur mahal yang dibuktikan

1. `runner._process_run()` membuat rencana dengan koordinat `MappingTarget` yang sudah dipin. Untuk kiriman, loop penulisan lama memanggil `grid.refresh()` lagi untuk alokasi slot. `writer.execute()` lalu memanggil `grid.refresh()` untuk setiap kelompok item. Koordinat tidak dicari ulang dari nol oleh planner, tetapi proof isi tujuan masih berulang.
2. `RegistryView.refresh()` boleh memakai fast path hanya bila token versi file sama dengan `MappingTab.content_revision`. POST robot mengubah versi **seluruh workbook**, sedangkan record tab lain masih menyimpan token sebelumnya. Karena itu penulisan pada tab sebelumnya membuat tab berikutnya jatuh ke jalur global. `expense_total` di BIAYA setelah biaya QRIS sangat mudah terkena kondisi ini. Tanpa Drive token, setiap refresh menggunakan proof global.
3. Jalur global: `read_destination()` → `DestinationReader.__init__()` → `sheet_properties()` + `_merges()` + `_scan()`. `_scan()` sebelumnya selalu melakukan `_header_values()` (values batchGet), `_groups()` → `_responses()` → `_ranges()` → `SheetsClient.request(GET)`. Seluruh allocated body dibaca melalui tile bounded dengan mask `FIELDS` yang memuat nilai, formula, **Note**, background dan format tanggal. Indeks hanya menyimpan predicate struktur; mayoritas Note/background biasa langsung dibuang setelah respons, tetapi tetap ditransfer dan di-parse.
4. Jalur setelah POST: `_submit_and_verify()` → `_verify_submission()` → `RegistryView.after_write()` → `refresh(force_global=True, allowed_changes=...)`. Ini diperlukan untuk membuktikan struktur/formula global dan perubahan finansial yang diizinkan, tetapi dilakukan **per item**. Kemudian `_verify_submission()` GET sel aktual lagi. Jadi target angka satu sel dapat menyebabkan pembacaan isi BIAYA besar baik sebelum maupun setelah POST.
5. `_responses()` membagi kelompok range bila `RESPONSE_TOO_LARGE`, sehingga percobaan besar yang ditolak pun mengonsumsi byte/waktu sebelum pembacaan ulang yang lebih kecil. Metadata `_merges()` juga bisa besar pada workbook sangat banyak merge. Membatasi sel target saja tidak menghapus kebutuhan bukti merge/global.

Fixture BIAYA ber-Note panjang mereproduksi jalur grid-data sampai 8 MiB dan 12 respons multi-megabyte. Tidak tersedia URL/mask dari log produksi Run #9, sehingga tidak diklaim bahwa setiap GET 7,7–8,3 MB produksi pasti grid-data, bukan metadata merge. Patch menambah klasifikasi log `read_kind`, jumlah range/sel, byte termasuk partial/rejected dan peristiwa `sheets_response_limit`, tanpa isi finansial/key. Klasifikasi `merged_geometry`, `global_cells`, `global_invariants`, `target_cells`, `drive_version` membantu membedakannya di VPS.

## Koreksi yang diterapkan

`batch_writer.process_plans()` mengambil rencana lengkap `MappedResult` dari mapping READY yang sama. Satu window memuat maksimum 64 kelompok, 8.000 sel dan payload di bawah cap lama 8 MiB. Kelompok fee/kiriman tidak dipotong. Setiap tab menjalani satu preflight; GET target/anchor dibagi hingga 32 sel per request. Prefetch planner KET hanya hipotesis awal, selalu dibaca ulang pada Stage C.

Preflight tetap memverifikasi seluruh struktur bila versi berubah. Pada tab yang dapat membuktikan **kedua extent header menutup lebar alokasi**, proof global memakai empat baris awal dengan mask lengkap, kemudian body dengan nilai/formula/format tanggal saja. Seluruh predicate tanggal, bank, TOTAL, website, fee/report dan formula tetap dipindai global. Empat baris lengkap mempertahankan warna hitam untuk header nomor hari KET. Bila bukti lebar/header tidak cukup, reader mengulang persis tile/mask V4.2, termasuk padding header. Tidak ada asumsi bahwa header cached membuktikan struktur body.

Sebelum POST, setiap kelompok melewati `validate_group()` dan `_execute_checked()` lama: kepemilikan, Note/manual/formula/merge, source authorization, ledger dan transfer intent PREPARED disimpan dahulu. Checksum rencana/snapshot diperiksa; `expense_total` memverifikasi input sukses yang menopang angka rencana tanpa mengulang sumber/sukses lain. Semua target kelompok di-GET ulang setelah persiapan SQLite, dibandingkan dengan observasi awal, dan epoch file/mapping/sumber/cancel diperiksa lagi. Konflik sel antar kelompok ditolak sebelum POST.

`SheetsClient.write_batch()` menggabungkan kelompok independen menjadi satu `batchUpdate` atomik dengan updateCells nilai/Note yang sama. Tidak ada append, clear area, format update, pemindahan koordinat, POST retry buta, atau concurrency baru. Sesudah HTTP tidak pasti, jalur lanjut ke readback, bukan POST kedua.

Readback berbagi `DestinationProof`: metadata properties+merge satu kali, global predicate proof satu kali per tab dan GET aktual seluruh sel yang ditulis. Epoch file harus ditutup stabil sebelum acknowledgement. Formula/global structure tetap wajib. `_verify_submission()` lama mengakui ledger setiap kelompok hanya jika semua nilai/deskripsi/Note cocok; kelompok gagal tetap PREPARED dan tidak menghalangi kelompok independen yang terbukti. Mapping signature yang diterima setelah penulisan sah dibaca ulang dari record durable oleh handle lain.

Jika token tidak tersedia, window dibatasi satu tab dan pembuktian header sebelum/sesudah tetap dijalankan. Jika metadata gabungan terlalu besar, kembali ke request scoped lama. Jika token hilang di tengah closed proof, seluruh window gagal pengakuan; intent dapat dipulihkan secara eksplisit. Global scanning yang tidak dapat dieliminasi tetap dilaporkan pada [INVARIANTS_V421.md](INVARIANTS_V421.md).
